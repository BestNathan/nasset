# Deribit archive operations

## Scope and source of truth

Operate **BestNathan/nasset** only. Read current `main` before deciding: `config/aws-deribit-scheduler.json`, `config/market-data-activation.json`, `config/market-data.yml`, `.github/workflows/aws-deribit-deploy.yml`, `.github/workflows/deribit-archive.yml`, `scripts/aws_deribit_scheduler.py`, `aws/deribit_dispatcher.py`, and relevant collector/publisher code. Read repository instructions first if present. Never treat this document's example times or paths as current evidence.

The managed AWS region is `ap-southeast-2`; the default schedule is `nasset-deribit-hourly`, `cron(12 * * * ? *)` in **UTC**. The Scheduler invokes Lambda `nasset-deribit-github-dispatcher`, which retrieves a GitHub token from SSM SecureString and POSTs `workflow_dispatch` to `deribit-archive.yml` on `main` with `publish=true` and the current UTC hour `slot`. GitHub runs `read-only-acceptance` then `publish` (only if checked-in activation is enabled), and writes to orphan branch `market-data`.

The native GitHub cron (`43 * * * *` in the workflow at time of writing) is an **independent trigger**. Never infer AWS delivery from an ordinary `schedule` run. Inspect actual workflow event, inputs and run timestamps. GitHub workflow_dispatch acceptance is not proof that the run succeeded.

## Evidence ladder — never collapse these stages

1. **Scheduler configuration / deployment**: inspect the latest deployment workflow run, its logs and current desired-state JSON. A green deployment and `state=enabled` support deployed configuration; they do **not** prove an invocation. To assert live AWS state, require an authorized live AWS status result; otherwise say it was not directly checked.
2. **Dispatch accepted**: inspect the Lambda execution evidence when AWS logs are actually available (sanitized `status=accepted` and HTTP status) and correlate a GitHub `workflow_dispatch` run with the expected slot. GitHub's presence proves a run was created; attributing it specifically to AWS requires supporting trigger provenance, not just its event type.
3. **Data persisted**: inspect the matching UTC slot's manifest and receipt in `market-data`; verify referenced Parquet objects exist, slot and dataset metadata agree, and publication evidence/commit is consistent. A successful `publish` job alone is insufficient. Never invent row counts, object sizes, commit SHAs, or receipts.

Report these three states separately as **verified / failed / unverified**, with exact URLs and UTC timestamps. A missing file is not a successful empty dataset. When permissions prevent a check, state the limitation explicitly.

## Investigation procedure

1. Establish current UTC time and expected hour slot, e.g. `2026-11-06T10:00:00Z` for the 10:12 UTC trigger. The timestamp is illustrative, not a target to replay.
2. Inspect `aws-deribit-deploy.yml` recent `main` runs, including job conclusions and failed-step logs; compare committed policy and the schedule expression generated by `scripts/aws_deribit_scheduler.py`. Distinguish policy from actual AWS status.
3. Inspect `deribit-archive.yml` runs around the expected UTC time. Select the `workflow_dispatch` run, not a `schedule` or `push` run. Check `read-only-acceptance`, the slot pin, `publish`, and errors. If run inputs are unavailable, do not assert the slot solely from start time.
4. Inspect the `market-data` branch's actual directory structure and locate the exact slot manifest/receipt using repository evidence. Parse both and verify every referenced data path exists; inspect integrity metadata where available. Do not assume a fixed path convention without checking the publisher implementation.
5. Compare the three evidence layers and record missing receipts, partial writes, duplicate slots, stale run attempts, or inconsistent counts. Link the exact run, manifest, receipt and commit where accessible.

## Failure matrix

| Symptom | Investigate first | Safe response |
| --- | --- | --- |
| Desired state enabled, no dispatch run | AWS schedule status, region, Lambda invocation/error metrics and logs **only if authorized**; SSM/IAM configuration | Report delivery unverified; do not claim CloudWatch inspection without access |
| Lambda reports GitHub 401/403/404 | PAT scope (Actions:write), repository/workflow path, token rotation, SSM permissions | Fix code/config through review; request secret rotation through approved controls, never print tokens |
| Dispatch exists, acceptance fails | activation, UTC slot freshness, Deribit probe, dependency install, API contract | Fix source/test defect; do not falsify slot or bypass probe |
| Acceptance passes, publish skipped | activation flag, event type, `publish=true`, job condition | Explain expected gating before changing anything |
| Publish fails | UTC rollover, branch write permission, conflicts, API throttling, manifest/receipt serialization | Diagnose from logs; preserve idempotency and existing archive |
| Publish green, receipt or data missing | actual `market-data` tree, publisher transaction boundary, object references | Mark persistence failed/unverified; repair and test before claiming success |
| Repeated run for same slot | receipt-based deduplication and publication race | Verify idempotent behavior; never overwrite valid data blindly |

## Safety and recovery

- Prefer **GitHub connector exclusively** for repository reads/writes when instructed. Do not use local git as a substitute. Never claim AWS API or CloudWatch visibility from GitHub evidence alone.
- Do not expose AWS AK/SK, GitHub PAT, SSM SecureString plaintext, Authorization headers, or raw secret-bearing logs. Do not request secrets in chat or commit them.
- Use a dedicated branch and PR for code, test, workflow, and documentation changes; preserve the existing `main` deployment gate. Avoid changes to `config/aws-deribit-scheduler.json` unless deployment is explicitly intended: pushes to that path trigger AWS reconciliation.
- Never invoke `disable`, `destroy`, token rotation, or an AWS reconciliation just to diagnose a missed slot. Do not rerun a historical slot as if its quotes were collected then: both Lambda and archive workflow reject stale/cross-hour slots.
- Before any replay, inspect current hour, receipt, existing run, and deduplication semantics; avoid duplicate publication. Make fixes through reviewed changes with focused tests and CI evidence.
- A fix is not verified until the appropriate new run and persisted receipt/data are checked. When AWS is inaccessible, state exactly which checks remain outstanding.

## Expected report

Use this compact structure: UTC slot; Scheduler desired state and independently observed AWS state; dispatch run ID/event and provenance confidence; acceptance/publish conclusions; manifest/receipt URLs; object count, rows and commit **only when verified**; error excerpts with secrets redacted; remediation/PR and outstanding checks. End with one of **persisted and verified**, **failed**, or **not yet verified**.
